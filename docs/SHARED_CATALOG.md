# Общий каталог и требования · 17 ноября 2026

Изменён существующий MVP по прямому запросу из «Вставленный текст.txt». Лендинг и другие репозитории не менялись, публичное размещение не выполнялось. Светлый интерфейс заменяет прежнюю тёмную палитру согласно этому запросу. Проверка, экономика, последовательный маршрут, сравнение и выпуск версий PDF сохранены.

## Что работает

- `/app/premises` — общий закрытый каталог агентства: создание без запроса, поиск по адресу/метке, площадь, базовая аренда, тип, подтверждённые мощность/вода/вентиляция. Есть пустое состояние и самостоятельная карточка.
- В запросе можно выбрать несколько существующих помещений либо создать новое. Повторный выбор не создаёт дублей; «Убрать из запроса» удаляет только связь. Объект, факты, проверки и отчёты сохраняются.
- Одна карточка используется в разных бизнес-профилях. Мощность 15 кВт даёт блокер для требования кофейни ≥25 кВт и соответствие для ПВЗ ≥15 кВт. Неизвестные, объявления и конфликтующие источники требуют уточнения.
- Группы требований: планировка, инженерия, доступ; нестандартные условия отдельно. Стандартные поля используют фиксированные единицы, границы «от/до», важность и наличие/отсутствие. Дополнительные характеристики свёрнуты. «Не важно» не подменяет неизвестное состояние объекта.
- Шаблоны кофейни, ПВЗ, магазина, салона и офиса применяются отдельным подтверждаемым действием. Они добавляют недостающие желательные условия без числовых нормативов. Смена названия бизнеса ничего не стирает.
- Фактические сведения сгруппированы аналогично требованиям. У каждого наблюдения есть источник, дата, область применимости, подтверждение и при необходимости ссылка на закрытый документ. История источников сохраняется.
- Общая правка предупреждает о влиянии на несколько запросов и требует подтверждения. Версия карточки делает все соответствующие оценки устаревшими. После отсоединения и повторного добавления старая оценка также не становится текущей.
- Интерфейс светлый: две колонки на широком экране, одна на телефоне, компактные карточки и раскрывающиеся дополнительные поля. Парсинг остаётся прежней заглушкой только для руководителя/администратора.

## Модели и сохранность

`Premises.agency` заменяет принадлежность одному запросу. `ClientRequest.premises` — M2M через `RequestPremises` с уникальной парой `(request, premises)` и проверкой совпадения агентств. Связь содержит адаптацию, прочие разовые расходы клиента, стрессовое допущение, допущения и внутренние заметки. Общая карточка хранит объективные технические и коммерческие сведения.

`Evaluation.request`, `context_version` и `link_identity` определяют конкретное сочетание запроса, объекта и исходной связи. Дополнительно проверяются версии профиля, карточки и правил (`p0-2.1`). Исторические проверки не перезаписываются; старые проверки предыдущих правил требуют пересчёта.

`Characteristic` — единый справочник из 27 стандартных характеристик с кодом, названием, группой, типом, единицей и допустимыми сравнениями. `Requirement` и `Observation` ссылаются на него через FK. Например, «Мощность» и «Электрическая мощность» мигрируют в `power_kw`; движок сравнивает идентификаторы. Пользовательские характеристики ограничены агентством и имеют стабильный собственный код. Переименование требования не меняет его идентичность. Прежние имена сохраняются.

`Observation.document` связывает факт с подтверждающим вложением. `Attachment.origin_request` сохраняет прежние ограничения доступа для уже загруженных файлов; новые технические документы общие только внутри агентства. Клиентские заметки не выводятся в каталоге или PDF. В общей карточке видны лишь те связанные запросы, которые пользователь вправе читать.

Миграция `0005_shared_catalog_data` добавляет поля и справочник, проверяет происхождение агентств, создаёт связи, переносит клиентские поля, привязывает оценки/вложения и нормализует параметры. `0006_remove_premises_adaptation_and_more` убирает старые перенесённые колонки и закрепляет NOT NULL. ID помещений, требований, наблюдений, оценок, вложений и отчётов сохраняются. Снимки оценок/отчётов и бинарные данные не изменяются. Эквивалентные записи единиц нормализуются без пересчёта физических величин. Несовместимые/неоднозначные старые требования сохраняются для ручного уточнения.

Если у старого объекта нельзя определить агентство, миграция завершается ошибкой с ID и откатывается транзакцией. Произвольного агентства по умолчанию нет. Обратная миграция допустима только для пустого каталога: заполненную новую модель нельзя без потерь свести к одному запросу на объект.

## Обновление существующей установки

Сначала проверьте перенос на отдельной копии. В период обновления остановите запись; не удаляйте том PostgreSQL.

```bash
docker compose stop web
sh scripts/backup.sh /secure/backup/leasefit
# Зафиксируйте прежний SHA/образ и проверьте восстановление копии.
git pull --ff-only
docker compose up -d --build
docker compose exec web python manage.py showmigrations leasefit
docker compose exec web python manage.py check
curl -f http://localhost:8000/healthz
```

При старте применяются миграции `0005` и `0006`. Проверьте каталог, исходные запросы, пересчёт и скачивание старого PDF. Для нового локального запуска используйте команды из [README](../README.md); `.env.example` остаётся без секретов. HTTPS и резервное копирование — [DEPLOYMENT.md](DEPLOYMENT.md).

Перед обновлением учебной базы сделана полная резервная копия. Сравнение всех исходных ID/значений после переноса подтвердило сохранность **5 запросов, 11 помещений, 8 требований, 17 наблюдений, 14 оценок, 5 отчётов и 1 вложения**; создано 11 связей. Клиентские поля сверены с исходными объектами, SHA-256 байтов каждого старого PDF и вложения совпали. Последующий браузерный тест добавляет отдельные вымышленные записи. В Git нет дампов, секретов, приглашений или содержимого учебной базы.

## Проверки

- Полный набор Django на PostgreSQL: создание независимой карточки, повторные/межагентские привязки, разные оценки для кофейни/ПВЗ, общие изменения и устаревание, частные заметки и старые файлы, отсоединение/повторное добавление, шаблоны, группированные поля и редактирование нестандартных условий, исходные правила P0, сравнение и PDF.
- `CatalogMigrationTests` создаёт записи в настоящей исторической схеме `0004`, затем применяет `0005`/`0006`; сверяет ID, клиентские поля, даты, справочник, JSON истории, бинарные файлы и повторный запуск миграций без дублей.
- Реальный Chromium: приглашение → два независимых помещения → группированный профиль кофейни → выбор каталога → блокеры и превышение 3 000 ₽ → PDF → ПВЗ и другая оценка той же карточки → общая правка и устаревание обоих результатов → пересчёт → удаление только связи → скачивание прежнего PDF с тем же SHA-256. Каталог, требования и сравнение проверены на 1440, 768 и 390 px без переполнения страницы и ошибок JavaScript.

Итоговые числа и команды — [TEST_RESULTS.md](TEST_RESULTS.md). Скриншоты и примеры PDF находятся локально в игнорируемом `artifacts/`.
